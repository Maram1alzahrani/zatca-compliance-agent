# Phase 8 — Scaled Synthetic Dataset

Status: **STABLE; FINAL TEST SEALED AND UNTOUCHED BY VALIDATORS**  
Date: 2026-09-06

## Objective

Scale the 12-case Phase 5 pilot into a deterministic dataset suitable for development, validation, and later unseen evaluation, while keeping invoice bytes, metadata, ground truth, and error-injection records separate.

## Dataset design

| Split | Cases | Compliant | Single injection | Multiple injections | Current use |
|---|---:|---:|---:|---:|---|
| Development | 48 | 8 | 15 | 25 | Development and debugging |
| Validation | 32 | 5 | 15 | 12 | Verification and tuning |
| Final Test | 32 | 5 | 15 | 12 | Sealed until Phase 13 |
| **Total** | **112** | **18** | **45** | **49** | — |

Each split covers all eight verified MVP rule groups. Variations include one to three lines, quantities, monetary values, invoice dates, issue times, synthetic seller/buyer names, item names, UUIDs, invoice identifiers, VAT identifiers, and single/multiple deterministic defects.

## Leakage controls

- Invoice filenames are neutral sequential names.
- XML payloads contain no rule IDs, labels, error types, or expected corrections.
- Metadata contains provenance and split information only.
- Ground truth and injection details are stored outside invoice directories.
- Case identifiers are opaque UUID-derived values and are disjoint across splits.
- No invoice-byte hash appears in more than one split.
- The agent will receive invoice content only; it will not receive ground truth or injection records.

## Ground-truth method

The generator starts from an internally consistent synthetic UBL invoice and applies named deterministic mutation operators. Every mutation records:

- target field;
- value before injection;
- injected value;
- expected original/correct value;
- expected internal rule IDs;
- whether automatic correction is safe under this synthetic case definition.

The expected rule set is the ordered union of the rules affected by all mutations in a case. One injected defect may create multiple valid findings, such as a line-net mutation causing both line and VAT-taxable reconciliation failures.

## Final Test isolation

`final_test_seal.json` stores SHA-256 digests for the Final Test manifest, metadata, injection records, and ground truth. The dedicated audit script rejects a request to inspect Final Test with validators. Phase 8 tests verify only dataset structure, hashes, determinism, coverage, and declared malformed XML; they do not run the compliance pipeline on Final Test.

The Final Test must not be used for rule changes, prompt tuning, retrieval tuning, correction policy changes, or agent orchestration decisions. Its first validator execution is reserved for Phase 13.

## Reproducibility

- Dataset version: `1.0.0`.
- Generator version: `1.0.0`.
- Independent fixed seed per split plus a deterministic per-case seed.
- Decimal arithmetic with explicit two-decimal half-up VAT rounding.
- A deterministic ZIP release is produced by `scripts/package_scaled_dataset.py`.

## Limitations

- The dataset represents only the frozen Standard Tax Invoice MVP profile.
- Synthetic diversity is not evidence of production data representativeness.
- Error operators target the eight selected rule groups, not complete ZATCA validation.
- Security features, signatures, hashes, QR, clearance/reporting, and broader ZATCA business rules remain out of scope.
- The Final Test is unseen by the validators but is still generated by the same generator family; this limitation must be stated in the final evaluation.

## Phase boundary

Phase 8 does not implement embeddings, retrieval, an LLM, tools, corrections, or evaluation metrics. Phase 9 may use only the verified Knowledge Base and Development/Validation resources while preserving Final Test isolation.
