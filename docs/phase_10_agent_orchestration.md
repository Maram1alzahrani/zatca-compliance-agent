# Phase 10 — Single-Agent Tool Orchestration

Status: **STABLE OFFLINE; OPTIONAL LIVE LLM CALL REQUIRES USER-SUPPLIED API CONFIGURATION**  
Date: 2026-09-06

## Objective

Connect deterministic invoice validation to verified evidence retrieval and grounded issue explanation through one auditable workflow agent. Phase 10 does not correct or modify invoices.

## Architecture decision

The workflow uses a deterministic state machine for mandatory tool selection:

1. Call `validate_invoice` exactly once.
2. For every `FAIL`, call `retrieve_zatca_rule` exactly once using the validator's internal rule ID.
3. If at least one failure exists, call `explain_issues` exactly once.
4. Return checks, grounded issues, and the complete tool trace.

The LLM is not allowed to skip checks, calculate VAT, validate XML, create rule IDs, choose citations, or decide compliance. This is intentional for reliability: the workflow itself determines required tool calls, while the optional LLM may rewrite only two narrative fields.

## Tool contract

| Tool | Responsibility | Explicitly excluded |
|---|---|---|
| `validate_invoice` | Secure parse plus eight deterministic selected checks | LLM reasoning and retrieval |
| `retrieve_zatca_rule` | Exact verified evidence lookup by failed rule ID | Lexical guess as the primary path |
| `explain_issues` | Deterministic narrative or bounded LLM narrative | Corrections, new rules, citations, approval claims |

Every tool call records sequence, name, sanitized input summary, output summary, status, and error type. Raw invoice XML and API credentials are not recorded in the trace.

## Explanation modes

- `not_required`: no failed checks.
- `deterministic`: grounded template with no LLM provider configured.
- `llm`: optional provider returned valid structured narratives.
- `fallback`: provider failed or violated the grounding contract; deterministic text was used.

Source references, official identifiers, applicability, rule meaning, and severity are always copied from the verified Knowledge Base. They are never generated by the LLM.

## LLM output guardrails

The optional provider may return only:

- `rule_id`;
- `issue`;
- `why_flagged`.

The application then verifies:

- IDs exactly match the ordered grounded findings;
- no missing, extra, or duplicated rule IDs;
- narrative fields are non-empty and bounded;
- no URL was generated;
- no `ZATCA Approved`, certification, official-compliance, or equivalent Arabic claim appears.

Any violation activates deterministic fallback. Provider exceptions are contained and do not erase validator findings or verified evidence.

## Optional OpenAI adapter

`OpenAIExplanationProvider` uses the Responses API structured parsing interface with a strict Pydantic output model. The model name must be supplied explicitly; the repository does not hard-code a model or store an API key. Optional dependencies are isolated in `requirements-llm.txt`.

The adapter contract and fallback behavior were tested without a network call. No live OpenAI request was executed in this phase because no API key is stored in the project. A live smoke test must be performed later with a user-supplied environment configuration before claiming live-provider reliability.

## Limitations

- This is a single workflow agent, not a multi-agent system.
- Default local output is deterministic; natural-language variation requires the optional provider.
- No live-provider latency, cost, refusal, or output-quality result is claimed yet.
- No correction, re-validation, final report, final metrics, or UI is implemented in this phase.
- Passing means only that the selected POC checks passed.

## Phase boundary

Phase 11 may add correction proposals, human approval, apply-to-copy behavior, and re-validation. It must not mutate the original invoice and must not auto-correct fields that require missing business information or human judgment.
